# Arch packaging and releases

The package includes optional desktop-integration examples in
`/usr/share/snipline/`: `snipline-autostart.desktop` and `bindings.md`.
It never installs an enabled autostart entry or modifies compositor settings.
The optional tray uses Qt Widgets (provided by the existing `qt6-base`
dependency); capture UI remains Qt Quick.

The root `PKGBUILD` builds and installs the application and its two helpers with
`BUILD_TESTING=OFF`. It does not build, run or install tests. `LICENSE` is MIT.
OCR models, editors and optional hardware-codec plugins remain optional.

## Repository still needs configuring

No GitHub remote was provided. The checked-in PKGBUILD therefore deliberately has
`OWNER/REPOSITORY` and an invalid checksum placeholder. It cannot download/build
a release until these are filled; integrity checking is never bypassed with `SKIP`.

Once a source release exists, populate it with:

```sh
python packaging/update-pkgbuild.py --repository OWNER/REPOSITORY --version 0.1.0
makepkg --printsrcinfo > .SRCINFO
makepkg -si --nocheck
```

Replace `OWNER/REPOSITORY` with the real repository. The script downloads the
release source archive and pins its SHA-256. `--archive /path/source.tar.gz`
instead hashes a local copy of that exact release archive.

## Release workflow

1. Push the project and workflows to GitHub.
2. Set the CMake project version and push a matching stable tag, such as `v0.1.0`,
   or dispatch **Release** with an existing tag.
3. The workflow builds in Arch Linux as a non-root `makepkg` user, without tests.
4. It publishes the tagged source archive, x86_64 Arch package, a correctly
   populated PKGBUILD, `.SRCINFO` and `SHA256SUMS` as a GitHub release.

Source archives use `snipline-VERSION/` as their root. Use the uploaded source
asset, not GitHub's differently structured automatic archive. The published
PKGBUILD uses the actual workflow repository, regardless of the initial placeholder.
Release creation requires the tag to already exist; it does not push tags or
overwrite an existing release. The application version comes from CMake.

## PKGBUILD update workflow

**Update PKGBUILD** runs after a published release, after our own successful
**Release** workflow, or manually. The workflow-run trigger is necessary because
events generated by `GITHUB_TOKEN` do not start another release-triggered workflow.

It downloads the published source archive, updates the repository URL, version
and checksum, generates `.SRCINFO`, and opens/updates a pull request on
`automation/update-pkgbuild`. It never publishes directly to the AUR or merges
the PR. Downgrades are rejected.

Enable **Actions → General → Workflow permissions → Allow GitHub Actions to
create and approve pull requests** in repository settings. The update workflow
needs contents-write and pull-requests-write permissions; release publishing
needs contents-write. No PAT or AUR SSH key is required.

These workflows require GitHub-hosted Linux runners with containers and network
access. They cannot be executed end-to-end in this checkout without a GitHub
repository and release. A local `makepkg --nocheck` build against a source snapshot
was successful; inspection confirmed that only the application/helpers/assets
were packaged, with no tests. The repository metadata in that private validation
package is a fixture, not a published release. Local validation:

```sh
python -m unittest discover -s packaging -p 'test_*.py'
bash -n PKGBUILD
```
